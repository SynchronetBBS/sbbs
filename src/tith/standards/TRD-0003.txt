────────

  This document describes how TITH can be used to construct a
  peer‐to‐peer network without a nodelist or assigned node addresses.

1. Introduction
───────────────

  A conventional FidoNet Technology Network assigns each member a
  numeric address and publishes the address, public key, contact
  information, and routing hierarchy in a nodelist.  This is not the
  only organization supported by the TITH data model.

  The "p2p" Domain reserved by TTS‑0004 describes a network with no
  assigned addresses, nodelist, coordinator, or administrative
  hierarchy.  Every peer has the same unlisted address and is
  distinguished by its public key.  Peers exchange the same Bundles
  and Messages used by nodelisted networks.

  This document describes one simple way such a network can operate.
  It does not define a mandatory routing or peer‐discovery algorithm.


2. Identity
───────────

  Every peer generates a signing key pair and uses the address
  "p2p#-1".  The identity of a peer is the combination of that address
  and its public key.  The complete identity therefore remains unique
  even though the address component is shared by the entire network.

  The public key proves continuity and possession of the corresponding
  private key.  It does not assert a person's name, reputation, or
  authority.  A peer which generates a new key has created a new
  identity unless some separately trusted mechanism establishes a
  relationship between the keys.

  Since there is no nodelist, the public key accompanying every
  unlisted Origin is the only key available for verifying its
  signature.  Every unlisted Destination is likewise accompanied by
  the public key of the intended recipient.


3. Neighbours and Bootstrap
───────────────────────────

  A peer needs the endpoint and public key of at least one other peer
  before it can join the network.  These may be configured manually,
  received in a signed invitation, or learned by another mechanism.
  TITH does not mistake endpoint discovery for authentication: a peer
  verifies that a connection uses the expected public key before it
  acts upon data received through that connection.

  Accepting a key presented for the first time by an otherwise unknown
  endpoint would authenticate the resulting exchange as that key, but
  would not establish that the endpoint is the peer the caller meant
  to contact.  A bootstrap mechanism must make that distinction clear.

  A peer may maintain a local table of neighbours, their keys,
  endpoints, observed availability, and routing information.  This is
  local operational state, not a nodelist: it need not be complete,
  globally consistent, centrally published, or shared in one format.


4. Bundle Exchange
──────────────────

  A Bundle describes one hop.  Its top‐level Origin is "p2p#-1"
  followed by the sending peer's PublicKey.  Its Header Destination is
  "p2p#-1" followed by the receiving peer's PublicKey.  The Header and
  payload signatures authenticate the sender and bind the intended
  recipient.  The receiver's Reply Bundle authenticates it in return.

  A NetMail Message inside that Bundle has its own Origin and
  Destination.  Both addresses are "p2p#-1", but each is followed by
  the public key of the corresponding end peer.  The Message signature
  binds those keys and all other end‐to‐end Message data.  An Echomail
  Message has an Origin and Area but no Destination.

  The Bundle identities and Message identities need not be the same.
  When a Message is forwarded, a new Bundle names the next pair of
  immediate peers while the enclosed Message is copied byte for byte
  as required by TTS‑0005.


5. Message Forwarding
─────────────────────

  If a peer has a direct route to a NetMail Message's Destination
  PublicKey, it can send the Message to that peer.  Otherwise it may
  queue the Message for one or more neighbours which might provide a
  route.

  A small network can use controlled flooding: each peer forwards a
  newly seen Message to every suitable neighbour except the neighbour
  from which it was received.  A larger network could maintain learned
  routes, use a distributed lookup system, or adopt another routing
  algorithm without changing the Message encoding.

  A routing decision is local.  It does not authorize modification of
  the signed portion of a Message.  RequestIdentifier, Via, SeenBy, and
  AdditionalKludgeLine retain the per‐hop rules specified by TTS‑0005.
  A Via for an unlisted peer includes its PublicKey, so the path can
  distinguish peers which all use the address "p2p#-1".

  A File attached to a Message travels with that Message.  A standalone
  File remains a one‐hop transfer and is not routed merely because the
  peers use the "p2p" Domain.


6. Echomail
───────────

  NetMail has one ultimate Destination PublicKey.  Delivering it
  through a peer network depends on some peer knowing a usable route
  toward that key.  Local routes may be incomplete, stale, or lost
  when peers disconnect, so routed NetMail in this model may be highly
  unreliable.  Per‐hop acceptance does not establish end‐to‐end
  delivery.

  Echomail is often a better fit.  An Echomail Message names an Area
  instead of an ultimate Destination.  Peers interested in that Area
  can replicate each newly seen Message across their subscribed
  neighbour links.  This resembles controlled flooding and does not
  require a globally correct route to any one peer.

  Replication also provides useful redundancy when individual peers
  are intermittent.  It does not guarantee that every interested peer
  receives every Message: that still depends on the connected graph,
  queue retention, and polling behaviour.  Duplicate suppression is
  especially important because the same Echomail may arrive through
  several neighbours.


7. Polling and Held Messages
────────────────────────────

  A peer may connect to a neighbour and send PollMessages from
  "p2p#-1" with its PublicKey.  The neighbour returns Messages in the
  queue associated with that key.  These may be Messages whose
  ultimate Destination is the polling peer or transit Messages which
  the neighbour selected for forwarding through it.  They may also be
  Echomail selected for replication over that neighbour link.

  A NetMail Message's ultimate Destination PublicKey remains inside
  the Message, and an Echomail Message's Area remains inside it.  A
  next‐hop queue association is local delivery metadata and does not
  replace or modify either value.  Consequently a transit peer can
  distinguish Messages it should consume from Messages it should
  continue forwarding or replicating.

  Queue retention, replication, retry timing, and storage policy are
  local decisions.  Accepted still means that a Message was
  validated, accepted, and stored; it does not promise eventual
  delivery by the peer network.


8. Duplicate Suppression
────────────────────────

  Address‐only SeenBy values cannot distinguish peers in this Domain
  because every peer uses "p2p#-1".  The duplicate acceptance record
  required by TTS‑0005 therefore also provides loop protection when a
  routing algorithm presents the same Message more than once.

  TTS‑0005 defines the authenticated Origin identity and end‐to‐end
  Signature as the stable identity of a signed item.  A peer which has
  already accepted that identity does not store, import, or forward it
  again, but returns Accepted for the current transmission.  This rule
  also handles a sender retry after an Accepted response was lost.

  TTS‑0005 requires accepted identities not to expire automatically.
  An administrator can explicitly remove them, with the consequence
  that a later copy can be accepted as new.


9. Trust and Administration
───────────────────────────

  The "p2p" Domain has no coordinator who approves identities and no
  nodelist which binds keys to organizational roles.  Each peer decides
  which neighbours it will exchange traffic with and which origin keys
  it trusts for local purposes.

  Removing the nodelist does not make peers anonymous to one another:
  their public keys are persistent pseudonymous identities and their
  signatures remain verifiable.  It removes the central assertion that
  an identity is a recognized network member with an assigned address.

  Admission controls, abuse handling, key revocation, endpoint
  advertisements, and reputation can be built above this model.  If
  peers need interoperable encodings or behaviour for those functions,
  they require separate standards rather than assumptions hidden in a
  local peer table.

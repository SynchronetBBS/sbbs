  This document describes how a prospective node may apply to join a
  FidoNet Technology Network using TITH.

1. Introduction
───────────────

  A node cannot use its permanent address until the network assigns
  one, but it must be able to exchange messages with the network in
  order to request that assignment.  TITH resolves this by combining
  the unlisted address defined in TTS‑0004 with a public key
  generated by the applicant.

  Enrollment does not require a separate application protocol.  An
  application and the coordinator's response are ordinary signed
  Messages.  Consequently they can be stored, forwarded, polled, and
  delivered using the same machinery as every other Message.


2. The Unlisted Address
───────────────────────

  The address whose Zone, Net, and Node are all negative one (−1) is
  the unlisted address for a domain.  In a domain which assigns listed
  addresses, every applicant uses that address, so it does not identify
  a particular system.  The public key accompanying the address
  supplies that identity.

  Before applying, the prospective node generates a signing key pair.
  The private key remains with the prospective node.  The public key
  accompanies the unlisted address and allows the receiving system
  to authenticate the Bundle and Message without finding the address
  in a nodelist.

  Possession of this private key establishes continuity between
  exchanges.  It does not establish membership in the network or make
  any claim in the application true.  Membership is established by
  the network's decision to place the node in its nodelist.


3. Applying
───────────

  The prospective node obtains a nodelist and selects an appropriate
  Administrative Node according to the rules of the domain.  It sends
  that node a signed Message whose Origin is the unlisted address
  and whose Origin PublicKey is the newly generated public key.

  The Message normally contains the information required to construct
  a nodelist entry, together with any additional information requested
  by the Administrative Node.  This information is Message content,
  not a fixed TITH form.  Different domains may have different
  nodelist formats, organizational structures, or admission policies.

  Acceptance of the Message at the transport layer means only that the
  Message was authenticated, accepted, and stored.  It does not mean
  that the application was approved.


4. Processing the Application
─────────────────────────────

  The responsible coordinator examines the application according to
  the rules of the domain.  The decision may involve communication
  with the applicant and need not be completed during the connection
  that delivered the application.

  Requests for clarification are ordinary Messages addressed to the
  unlisted address and its public key.  Replies from the applicant
  are ordinary Messages signed with the same key.  This exchange may
  continue for as long as required by the domain.


5. Receiving the Decision
─────────────────────────

  A Message addressed only to the unlisted address would be
  addressed to every prospective node.  A held Message for an
  applicant is therefore associated with both the unlisted address
  and the applicant's public key.

  The prospective node periodically sends a PollMessages request from
  the unlisted address, authenticated using the same public key.
  The receiving node returns only Messages held for that key.  The
  coordinator can use such a Message to report approval, denial, ask
  for more information, or provide any other human‐readable details.

  Retention periods, expected polling frequency, and the consequences
  of an abandoned application are local policy.  They do not change
  the identity of an applicant or the meaning of a PollMessages
  request.


6. Approval
───────────

  Approval assigns an address by adding an entry to the domain's
  nodelist.  The entry associates the assigned address with the same
  public key that authenticated the application.  The applicant then
  uses the assigned address and existing private key in place of the
  unlisted address.

  A Message from the coordinator can notify the applicant of the
  assigned address, but the nodelist is the authoritative statement
  that the address has been assigned.  A denial leaves the applicant
  unlisted; its explanatory Message does not require a special
  protocol status or error value.


7. Network Policy
─────────────────

  TITH defines the mechanism used to exchange and authenticate an
  application, not the authority to approve it.  Each domain decides
  which Administrative Node receives applications, what information
  is required, who may approve them, and how a decision may be
  appealed.

  FidoNet Policy 4 is one example.  It directs an applicant to send
  netmail to node zero of the applicable network or region, describes
  the information expected in that request, and recognizes the
  traditional negative‐one address for applications.  Those provisions
  are useful background for FidoNet, but do not govern other domains.

  FSP‑1016 attempted automated point enrollment using temporary
  addresses, passwords, control files, and later polling.  The useful
  general concepts are an applicant identity, an asynchronous
  decision, and a retrievable response.  TITH obtains those properties
  from the applicant's public key and its existing Message and Poll
  operations, without carrying forward the temporary addressing and
  password machinery.

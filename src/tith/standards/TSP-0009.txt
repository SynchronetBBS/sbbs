Abstract
────────

  This document binds TSP‑0004 local IPC documents to loopback TCP.  It
  defines fixed mutual public‐key authentication, encrypted line
  records, caller identity, connection completion, and recovery using
  libhydrogen.  It is intended as the portable socket binding,
  including on Windows.

1. Introduction
───────────────

  TCP provides a portable reliable byte stream but does not identify a
  local caller or authenticate the listening Service.  Sending an IPC
  document directly over a loopback connection would expose Source
  pathnames and Message contents to an impersonating listener and would
  let any local connector claim an Application.

  This binding therefore has mandatory mutual authentication and
  encryption.  It uses the libhydrogen Noise KK key exchange and
  secretbox operations already available to TITH.  There is no
  password, certificate format, security option, algorithm choice, or
  negotiation.

  The authenticated Client static key is the TSP‑0004 caller identity.
  The Client authenticates the configured Service static key before
  transmitting any request line.


2. Endpoint and Static Keys
───────────────────────────

  The Service listens on one TCP port selected by trusted host
  configuration.  Every listening address MUST be an IPv4 or IPv6
  loopback address.  It MUST NOT bind a wildcard or nonloopback
  address.  After accepting, the Service also verifies that the remote
  address is loopback before beginning authentication.

  The Service and every authorized Client each have a dedicated
  hydro_kx static key pair generated by hydro_kx_keygen().  A key pair
  used by this binding MUST NOT be reused as a TITH signing key, Bundle
  identity, or key for another protocol.

  Trusted Client configuration contains the exact Service
  hydro_kx public key.  Trusted Service configuration maps each exact
  authorized Client hydro_kx public key to one local IPC principal and
  its permitted Applications and operations.

  A public key in configuration is the 43‐character base 64
  representation of its 32 bytes with the trailing Equals Sign
  (U+003D) removed.  Public keys are compared as their exact 32 decoded
  bytes.  Secret keys MUST be protected from other local principals.


3. Authenticated Key Exchange
─────────────────────────────

  Immediately after TCP connection establishment, the Client sends,
  in this order:

    • the eight ASCII bytes of the literal "TITHIPC1";
    • its 32‑byte hydro_kx static public key; and
    • the 48‑byte packet produced by hydro_kx_kk_1().

  The Client calls hydro_kx_kk_1() using a new hydro_kx_state, the
  configured Service public key, and its own static key pair.  TCP may
  segment these 88 bytes arbitrarily; the Service reads their exact
  lengths and MUST NOT interpret partial fields.

  The Service verifies the literal, looks up the transmitted Client
  public key, and calls hydro_kx_kk_2() using that exact key and its own
  static key pair.  Failure or an unknown key closes the connection
  without an IPC result.  Success produces the Service session keys
  and one 48‑byte response packet, which the Service sends exactly.

  The Client reads that complete packet and calls hydro_kx_kk_3() with
  its saved state and static key pair.  Failure closes the connection
  without sending a request.  Success authenticates the configured
  Service and produces the Client session keys.

  The Client MUST NOT transmit an encrypted request record before
  hydro_kx_kk_3() succeeds.  The Service MUST NOT parse an IPC request
  before hydro_kx_kk_2() succeeds.  No handshake byte is part of the
  TSP‑0004 document.

  For each side, the hydro_kx tx key encrypts records it sends and its
  rx key decrypts records it receives.  Session keys and key exchange
  state are erased when the transaction ends.


4. Encrypted Line Records
────────────────────────

  Every physical TSP‑0004 line, including its terminating Line Feed,
  is one encrypted record.  The sender encrypts the complete line with
  hydro_secretbox_encrypt().  The context is the eight bytes of the C
  string "TITHIPC", including its trailing NUL.  The key is the
  direction's hydro_kx session key.

  msg_id is an unsigned 64‑bit record sequence number.  It begins at
  zero independently in each direction and increments by one after
  every successfully encrypted or decrypted record.  A repeated,
  skipped, reordered, or unrepresentable next msg_id fails the
  connection.

  A record consists of the ciphertext length encoded as one canonical
  TTS‑0002 unsigned integer, followed immediately by that many
  ciphertext bytes.  The length includes the
  hydro_secretbox_HEADERBYTES overhead.  It MUST be greater than that
  overhead and representable safely by the receiver.

  The receiver reads the complete declared ciphertext, decrypts it with
  hydro_secretbox_decrypt(), and acts on no plaintext from a failed
  record.  Successful plaintext MUST contain exactly one nonempty IPC
  physical line: its final byte is Line Feed and no earlier byte is
  Line Feed.  The normal TSP‑0004 lexical parser then validates it.

  An IPC line may be of arbitrary length.  This binding does not impose
  a plaintext record limit.  Checked allocation, the receiver's size
  representation, available memory, and local resource policy remain
  applicable and cause connection failure rather than truncation.

  The ciphertext length is framing, not authenticated IPC data.
  Changing it cannot produce accepted plaintext: a short, long,
  truncated, or modified ciphertext fails decryption or connection
  framing.


5. Connection Transaction
─────────────────────────

  One authenticated TCP connection carries exactly one transaction.
  After key exchange, the Client sends the TSP‑0004 request one
  encrypted line record at a time through its final outer End.  It then
  sends no more records and keeps the connection open.

  The Service processes the complete request and sends its one result
  through the final outer End, also one encrypted line record at a
  time.  Completion is determined from the authenticated document, not
  TCP FIN.

  After receiving and validating the complete result, the Client
  performs the active close.  The Service sends no more bytes and waits
  for Client closure.  It MAY close after a local inactivity timeout;
  such a close cannot change a result the Client already completed.

  The encrypted records decode to the exact TSP‑0004 document bytes.
  The binding does not add a decoded length prefix, character
  conversion, Null, or alternate newline.


6. Failure and Recovery
───────────────────────

  An invalid literal, unknown key, key exchange failure, ciphertext
  framing error, decryption failure, unexpected record, TCP failure,
  or premature close terminates the connection.  No unauthenticated or
  partially decrypted Error is returned.

  After authentication, an ordinary malformed IPC request may receive
  an encrypted TSP‑0004 Error when its record and outer framing permit
  one.  The Service never sends plaintext fallback data.

  If the Client does not completely decrypt and validate the result,
  the transaction outcome is unknown.  It applies the operation's
  idempotency, Query, and recovery rules.  For Submit it first uses
  Lookup-Submission on a new authenticated connection.  If necessary
  while every Source remains available, it may retry the identical
  Submit request with the same idempotency keys.


7. Operation Restrictions
─────────────────────────

  TCP cannot transfer a native open handle.  This binding supplies no
  associated handle table.  A TSP‑0006 Submit request containing
  Source-Handle produces a Not-Committed Invalid failure.  Source-Path
  remains available and refers to the Service host's filesystem.
  Capabilities omits the feature "Submit.Source-Handle".

  All other TSP‑0004 operations, including Events Wait, use the normal
  transaction.  A waiting operation keeps its authenticated connection
  open until its result or a temporary failure.


8. Security
───────────

  Loopback restriction is mandatory but is not authentication.  The
  Service authorizes against the Client public key authenticated by
  hydro_kx KK.  An Application or key written inside encrypted request
  text does not replace that principal.

  The Client MUST authenticate the configured Service key on every
  connection.  Trust on first use, an unverified replacement key, and
  continuing after hydro_kx failure are prohibited.

  The greeting exposes the Client public key and connection timing to
  other local software.  The request, result, and their line contents
  are encrypted and authenticated.  Record lengths remain visible.

  Implementations apply timeouts and resource policy to incomplete
  greetings, key exchanges, length prefixes, ciphertexts, requests,
  results, and waiting operations.  A failure never permits plaintext
  fallback or processing of unauthenticated request data.


9. Feedback and Discussion
───────────────────────────

  The fixed key exchange makes TCP useful on Windows and other systems
  without depending on Unix peer credentials.  Dedicated static keys
  also avoid importing certificate parsing, password storage, or an
  optional security mode into a small local protocol.

  One encrypted record per IPC line preserves incremental parsing and
  exact outer End framing without imposing a whole‐document buffer or
  a protocol line‐length limit.
